# ADR-0006 事件与表格式的冻结与变更流程

- **状态**：已接受（2026-10-20）
- **决策者**：项目负责人
- **相关**：ADR-0002（指标可复算）、ADR-0005（24 表 + 事件 seq/幂等键）、`phase1.1-scope-and-acceptance.md`

## 1. 背景

`run_events` 是**可重放的真相源**，`store_meta.schema_version` 与 `run_events.schema_version` 决定了三个月后能否读懂今天的事件。
Phase 0 曾因"表结构悄悄变了、旧数据读不出来"踩过坑；Phase 1 目前只有 `schema_version = "1.0"`，**没有变更流程**。

## 2. 决策（两条纪律）

### D1：`1.0` 冻结

- `run_events` 的字段集合、字段语义、`type` 枚举、`payload` 必填键，**以本文档日期为准冻结为 v1**。
- 冻结意味着：任何**破坏性**修改（删字段、改语义、改枚举值、改 payload 必填键）都需要升版本 + 本文档追加条目。
- **非破坏性**修改（新增可选字段、新增 `type` 值、新增 payload 键）**不需要**升版本，但必须追加到 §4 登记表。

### D2：相邻迁移，不跳版本

- 事件格式版本与 `store_meta.schema_version` 必须**成对**升级（`1.0 → 1.1`）。
- 升级必须提供：①旧版本**冻结解码器**（只读，不允许再改）；②`vN → vN+1` 的**相邻迁移函数**；③迁移的幂等测试（跑两次结果一致）。
- 禁止"跨版本直接改"（`1.0 → 1.2` 必须拆成两次相邻迁移）。

## 3. 为什么不做"完整多版本链"

DSH 有 `v0→v1→…→v4` 五个冻结解码器，那是**面向外部消费者**的产品级需求。
本项目只有一个消费者（自己），**过度设计会拖垮进度**。因此只要求：**v1 冻结 + 一次变更走完整流程**即可证明机制成立；第二次变更时再按同样流程复制。

## 4. 变更登记表

| 日期 | 版本 | 变更 | 类型 | 迁移 | 测试 |
|---|---|---|---|---|---|
| 2026-10-20 | 1.0 | 初始冻结（无变更） | — | — | `tests/integration/test_events_replay.py` |

## 5. 约束（可执行）

1. `lit_agent.db.session.verify_schema` 必须能报告 `schema_version` 与缺表缺列（已实现）。
2. 任何 `1.x` 升级必须同时更新：`phase1.1-scope-and-acceptance.md` 的版本号、本文档 §4、`RESULTS-P1.md`。
3. 事件 `type` 的新增必须同步 `lit_agent/models/event.py` 的 `EventType` 枚举与 API 文档（`docs/api/openapi.json` 不覆盖事件类型，需在 guide 中列）。
4. 违反 D1/D2 的改动**不得合并**，即使测试是绿的。

## 6. 后果

- 正面：旧事件可读、回放可信；schema 漂移会在 CI/基线里被发现而不是在答辩前夜。
- 负面：每次破坏性变更多约 0.5 天（解码器 + 迁移 + 测试）；这是有意的成本。
