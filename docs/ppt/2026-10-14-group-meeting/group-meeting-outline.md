## 1.2 LangChain 家族的真实架构（先纠正一个误解）

**要点（讲这句就够）**：LangChain 不是"每个模块都自研引擎"的框架，它本质是 **抽象层 + 集成包装层 + 少量自研实现**；真正的能力来自第三方库。而且 v1 做过一次大重组——旧 chains / AgentExecutor / memory 迁到独立包 `langchain-classic`，**编排正式交给 LangGraph**。

| LangChain 组成 | 性质 | 底层真身 |
|---|---|---|
| `langchain-core` | **自研抽象层** | Runnable/LCEL、messages、tools、prompts、output parsers、callbacks、retrievers 基类 |
| `langchain`（v1） | 自研（薄） | 基于 LangGraph 的 agent API（`create_agent`）+ middleware |
| `langchain-classic` | 自研（维护模式） | 旧版 chains、AgentExecutor、memory |
| `langchain-community` | **包装集合** | pypdf、Unstructured、BeautifulSoup、rank_bm25… |
| `langchain-<provider>`（openai/anthropic/ollama…） | **包装** | 各家官方 SDK / HTTP API |
| `langchain-<vectorstore>`（qdrant/chroma…） | **包装** | 官方客户端（qdrant-client 等） |
| `langchain-text-splitters` | 自研（小） | 递归/语义分块 |
| `langgraph`(+`langgraph-checkpoint-*`) | **自研引擎** | 图状态机 + checkpoint + 流式 |
| `langserve` | **包装** | 把链暴露成 FastAPI 路由 |
| `langchain.evaluation` / LangSmith | 自研 hooks / **SaaS** | 评测与追踪服务 |

**结论句**：真正自研的只有**编排（LangGraph）、旧链与记忆、分块、检索器基类、回调**；模型、向量库、解析、加载器**都是对第三方的薄包装**——"用 LangChain 的某个模块"往往等于"**多一层包装去调用同一个第三方库**"。

## 1.3 逐模块：为什么不用它自带的模块

| 本项目模块 | 对应 LangChain 模块 | 用不用 | 不用的架构级理由 |
|---|---|---|---|
| 模块2 网关/路由 | `langchain-<provider>` 模型类 | ❌ | provider 差异被再抽象一层；熔断/成本/敏感度策略要改链路代码；LiteLLM 更贴协议层，且 fallback/成本表由上游维护 |
| 模块5 向量库 | `langchain-<vectorstore>` | ❌ | 单向量库场景官方客户端更直接；包装层会裁剪 payload 过滤/本地模式/量化等全功能 |
| 模块6 文档加载 | `langchain-community` loaders | ❌ | 传递依赖重（Unstructured 等）；输出 `Document` 元数据仍需二次归一化；本项目源固定 |
| 模块6 分块 | `langchain-text-splitters` | ❌（唯一可单包引入） | 分块必须与本地 embedding/模型 token 预算严格对齐；自研约 50 行更可控 |
| 模块5/1 检索 | LangChain retrievers | ❌ | 检索过程被抽象隐藏；本项目要显式控制过滤、去重、novelty、证据卡格式，评测要看到每一步 |

| 模块1 编排 | **LangGraph** | ✅ **采用** | 家族里最新、最对口的一层，可脱离经典 LangChain 独立使用 |
| 模块10 评测 | `langchain.evaluation` / LangSmith | ❌ | LangSmith 是 SaaS（数据出境 + 付费）；漂移/自愈等领域指标必须自研，标准指标用 DeepEval |

| 横切 追踪 | callbacks | ❌（作真相源） | 事件表是回放/评测/审计的真相源，不能绑在框架回调抽象上 |

## 1.4 "不适合当前项目"的五个具体点（这是导师最想听的"证据"）

1. **声明式组合 vs 条件控制流**：LCEL/链擅长"拼管道"，难以自然表达"**漂移→回退、失败→降级、超预算→中断**"这类条件跳转；图式编排才直观——这也是官方把编排迁到 LangGraph 的原因。
2. **隐藏的提示词与工具格式**：框架自带 prompt 模板与工具调用约定，模糊了"模型到底看到什么"，直接影响**可复现性与论文可控性**。
3. **抽象泄漏**：异常类型、流式事件、重试行为都经过多层包装，排障要翻两层。
4. **版本耦合**：`langchain-core` 与各集成包版本矩阵强绑定；v1 大迁移把 chains 整体搬走（旧代码 `import langchain.chains` 直接失败）→ 对一年制项目是实打实的维护风险。
5. **依赖过重**：loader/retriever 生态带入大量传递依赖，与"**单机、轻依赖、零外部服务**"的目标冲突。

**我们的采用边界**：采用 **LangGraph（编排内核）+ 其依赖的 `langchain-core` 类型体系**；不用经典全家桶；将来若真有"语义分块/特殊格式加载/跨向量库"需求，**只装对应单包**（分模块、轻依赖）。

**一句话口径（背下来）**：
> 不用经典 LangChain，不是因为它是自研框架，而**恰恰因为它大部分是对第三方库的薄包装**：这些包装与我已选定的更专业组件（LiteLLM 网关、官方向量客户端、自研解析/分块）职责重合，还带来版本耦合、隐藏提示词与依赖负担。我采用的是**同一家族的新一代编排引擎 LangGraph**——用家族里最新、最合适的一层。

## 1.5 编排内核：三选一对比

| 维度 | **LangGraph**（采用） | **AutoGen**（微软） | **OpenAI Agents SDK** |
|---|---|---|---|
| 设计中心 | 把 agent 流程当**状态机**工程化 | **多 agent 对话/协作**研究 | 快速做 **agent 应用**的极简套件 |
| 控制流 | 显式 node + 条件边（看得见图） | 由对话轮次/发言者选择隐式决定 | 由 handoff 交接驱动 |
| 状态与恢复 | 内建 checkpointer，**恢复粒度=节点边界** | 有状态管理，恢复偏会话层 | Sessions 管会话记忆，长跑恢复自管 |
| 多 agent | supervisor/swarm/子图/Send API | 群聊、团队、事件驱动 actor 运行时 | handoffs、agents-as-tools |
| 可观测 | LangSmith（可选） | 自带事件与 tracing | 内建 tracing，**默认上报 OpenAI 平台** |
| 供应商中立 | 完全中立（改 `base_url`） | 中立（支持多家） | **OpenAI 优先** |
| **面向谁/什么场景** | 要把 LLM 编排**嵌进产品后端**的工程团队：多阶段流水线、人工审批中断、长跑恢复、时间旅行调试 | **研究者/实验者**：验证多 agent 协作模式、涌现行为、对话协议；快速搭"多 agent 一起干活"的原型 | **应用开发者/创业团队**（尤其 OpenAI 生态内）：客服、任务自动化、多步工具调用，追求最短落地 |
| 为什么不用 | — | ①控制流藏在对话里→守卫不可单测；②恢复粒度偏会话层；③v0.2→v0.4 大重写 + 2025 年并入 Microsoft Agent Framework（换代风险） | ①偏 OpenAI（tracing 默认上报）；②其 guardrails 是**输入/输出校验**，不是我们需要的**阶段级守卫 + 升级阶梯**；③长跑恢复要自管；④可评审性弱于显式图 |
| 备注 | 我们实测 1.2.12 + checkpoint-sqlite 3.1.1 | — | **保留给 Chat 页局部使用**（与主流水线不冲突） |

**一段话裁决**：
> AutoGen 是"**多 agent 对话研究**"的框架，OpenAI Agents SDK 是"**快速做 agent 应用**"的套件，LangGraph 是"**把 agent 流程当状态机来做工程**"的运行时。我们要的是第三种：**阶段可枚举 + 守卫可判 + 崩溃可续 + 全程留痕**，而论文贡献在 harness 模式与评测，不在重造运行时。

## 1.6 LLM 网关：三选一对比

**网关必须干四件事**：统一接口（云 DeepSeek + 将来本地 Ollama/vLLM）、路由（敏感度强制本地 + 复杂度/成本选档）、熔断降级重试、计量入事件。

| 方案 | 优点 | 缺点/风险 | 适配 |
|---|---|---|---|
| **LiteLLM**（采用，SDK 进程内） | 统一 100+ 家；内置 fallback/重试/负载均衡/成本与预算；OpenAI 兼容端点（DeepSeek/Ollama/vLLM）直接注册 | 多一层抽象、需锁版本；**业务路由仍在我们代码层** | ★★★★★ |
| 自研薄网关（~300 行） | 零依赖、全可控、与事件溯源天然一体 | 重试/熔断/成本/多厂商适配全要自己维护 → 可维护性弱，与"框架优先"取向冲突 | ★★★ |
| **OpenRouter** | 免运维聚合、一个 key 数百模型、自动选 provider 与 fallback | **第三方中转**（数据出境）、**不支持本地引擎**、会吞掉我们必需的失败留痕、加价 | ★★ |

**OpenRouter 到底是什么（若导师问）**：**托管型模型聚合/路由服务**——一个 API Key、OpenAI 兼容接口，访问数百模型/数十家 provider。它提供的云上服务包括：统一计费与额度、按价格/延迟/吞吐**自动选 provider**、provider 宕机/限流时**自动 fallback**、模型横评与排行榜、用量面板、**provider 数据政策筛选**（可只走不记录/不训练的 provider）、BYOK、部分 `:free` 模型。**面向**：独立开发者/爱好者（一个 key 试遍模型）、创业团队（快速接多模型 + 可用性兜底）、做模型横评的人、所在地区拿不到某家 API 的人。

**为什么不用它（四条硬理由）**：
1. **数据出境/第三方中转**：我们设计里"敏感度强制走本地"是**代码层**约束，多经一手与"本地优先 + 隐私"冲突；
2. **无法承担"统一网关"职责**：它只能路由托管的云 provider，**不支持我们的本地引擎**（Jetson 档）；
3. **可观测与守卫必须在我们手里**：熔断/降级是要写进事件与评测的事实（升级阶梯、`E_PROVIDER_TIMEOUT`、预算 80%/100%）。被它的自动 fallback 吞掉，失败留痕与检出率就失真——**实测证据**：我们曾"超时只写日志没写事件"，导致指标里 timeout 族检出率**恒为 0**；这类问题只能在自己调用边界上解决；
4. **成本与依赖**：直连 DeepSeek 是最短路径（成本已低至 **$0.006/run**），中转引入加价与额外可用性依赖，且成本/时延口径变得不可比。

**诚实补充（导师会欣赏分寸）**：**LiteLLM 本身把 OpenRouter 当作一个 provider**，需要时一行配置即可接入；我们只把它保留给**一次性模型横评**（离线、非关键路径），不放进运行时。

## 2.0 总览：7 个重难点 + 三层防线

| # | 重难点 | 为什么关键 |
|---|---|---|
| 1 | **长时运行的方向固定与自愈机制**（导师强调） | 每周无人值守长跑，漂移/循环/幻觉会级联放大 |
| 2 | 论文关联与作者动向分析（导师强调） | 关系与度量口径难定；同名消歧是公认难题 |
| 3 | 多 agent 长跑中的上下文管理与折叠 | 长 run 状态膨胀，窗口/显存受限 |
| 4 | 双引擎路由在无人值守下的稳定性与成本 | 云故障/限流/成本失控都要自动兜底 |
| 5 | 增量同步、去重与幂等 | 周更正确性的地基；重复/漏抓污染评测 |
| 6 | 可观测、回放与确定性复现 | 评测与自愈测试都依赖"能重放现场" |
| 7 | 无人值守运维 | 进程重启/锁/存储增长/磁盘 |

**三层防线（一句话讲清自愈体系）**：
```
防线1 运行时守卫（每节点前后）→ 防"跑偏"：漂移/循环/停滞/schema/引用 检测 → 条件边
防线2 状态机纪律（全局）      → 防"失控"：结构化产出 · 超时/轮次上限 · checkpoint · 升级阶梯
防线3 事后质检与反哺（run 末）  → 防"劣质产出过关"：quality_guard + judge + grounding → 重写/标注
```
**升级阶梯（统一）**：`retry(≤2, 退避) → degrade(换模型档/换源) → replan(回退到 planning/scoping) → abort + annotate(留痕，不阻塞下周)`

## 2.1 代表性问题 ①：怎么保证"防走偏"（A1，导师最关心）

**为什么难**：一次周更跨小时级、无人值守；早期一步跑偏会被后续放大。不可能承诺"零漂移"，只能做到 **有界、可检出、可回退、可量化**。

**架构级方案（八条；PPT 第 8 页取其中 7 条，预算一条单独成页 —— 逐条去向见下）**：

| # | 方案 | PPT 去向 |
|---|---|---|
| 1 | **Scope Anchor 单一基准**：topic 的 `scope_statement`（目标 + 边界 + **反例说明**）版本化、只能显式编辑；所有节点 system 注入它 | 第 8 页 Methods 第 1 条 |
| 2 | **显式阶段图 + 出入契约**：每 stage 声明输入/输出 schema 与通过条件，节点间插 validator，**不允许跳阶段** | 第 8 页 Methods 第 2 条 |
| 3 | **证据优先产物契约**：每条断言必须带可回查 citation；无支撑标"未证实"，不允许静默编造 | 第 8 页 Methods 第 4 条 |
| 4 | **检索硬约束在代码层**：源白名单、时间窗、去重指纹用代码强制，**不靠提示词** | 第 8 页 Methods 第 5 条 |
| 5 | **预算与看门狗制度化**：token/时间/成本/轮次上限 + 节点超时 + 递归上限 | **移到第 10 页**（预算专页，避免与"四维看门狗"重复） |

| 7 | **角色分离 + 最小上下文**：检索/分析/写作各看该看的；critic 只审不写且**异源** | 第 8 页 Methods 第 3 条（与"异源 critic"合并为一条） |

## 2.2 代表性问题 ②：死循环与停滞（A2）

**为什么难**：多 agent 长跑常见"同一查询反复调用""摘要复述无新增"，token 成本线性上涨而无产出。

**设计**：
- 状态机**禁止无限循环**——条件边只允许有限次回退，每次回退计数入状态，超限强制终止并 annotate；
- 三级检测：①工具调用签名（工具名+规范化参数哈希）滑动窗口成环；②状态哈希重复；③"已核实事实集合"增量=0 判停滞；
- 处置阶梯同上（retry→degrade→replan→abort）。

**已实测**：循环注入 3/3 检出，**首次 replan → 再次 abort，6 步内终止**（不空转烧预算）；停滞注入 3/3 检出（首次 degrade 换源 → 持续 abort）。


## 2.3 代表性问题 ④：预算失控（A4）

**为什么难**：无人值守时成本没有上限会失控；而"跑到自然结束"是常见的错误默认值。

**设计**：预算是一等公民——**run 级**（token/时间/成本）+ **节点级**（超时）+ **图级**（递归上限）；接近上限**提前降级**（换便宜档、缩短检索批次），超限即终止并 annotate。
**已实测**：4 维看门狗（tokens/seconds/cost/steps），**80% warn（不阻断）→ 100% stop（abort）** 阶梯完整可见，注入检出 3/3。


## 2.4 代表性问题 ⑥：幻觉与事实性（D 类）

**四条设计（讲"契约层强制 + 显式呈现分歧 + 拒答合法"）**：
1. **D1 claim→evidence**：报告以"断言 + 证据引用"为基本单元；**无引用的断言在 schema 层不被接受**；citation 必须能在语料快照中定位（paper_id + 片段），定位失败 → 标"未证实"并计入幻觉率；
2. **D3 矛盾处理**：矛盾是**一等状态**（记两条证据 + 分歧点），报告**必须显式呈现分歧而非取平均**；高影响矛盾触发人工复核标记；
3. **D4 拒答合法**：契约里明确"证据不足"是**合法输出**（拒答不计失败），且要说明"缺什么证据/怎么补"；
4. **D2/D5**：进入结论的数值必须来自工具结果并保留来源；跨源冲突不擅自取一；显式区分"发表/更新/发现"三种时间语义。

**已实测**：S5 强制"citation 回查不到语料的 claim 整条丢弃并计数"；S7 的手工抽查证实事件侧与 claims 文件**完全一致**（16/1/6/23），citation 可回查率 1.0、越界副作用率 0。


## 2.5 代表性问题 ⑦：长跑上下文膨胀（C 类）

**设计**：①**LangGraph 状态只存结构化摘要 + 指针**（paper_id/事件 id），不存原文；②每次模型调用前计算预算，超预算**先折叠再调用**，折叠是**显式节点**；③三层记忆（topic 长期状态 / 证据库 / 周报历史）各有读取接口，**禁止全量倒进上下文**；④固定注入槽：system（scope+状态+政策）/ user（当前任务）/ tools（带引用的结果卡）。
**当前状态**：设计完成，Phase 0 未压测（数据量小）；列入 Phase 1（长跑压测 + 折叠粒度实验）。


## 2.6 代表性问题 ⑨：工具返回值不可信（B1，设计感最强的一条）

**为什么难**：MCP/工具返回是**不可信数据**；"合理"其实包含协议合规、数值域、跨字段一致、语义成立**四类不同问题**，混在一起就会"什么都问 LLM"（贵且不稳）。

**四层判定管线（前四层都不需要 LLM）**：

| 层次 | 检查内容 | 方法 |
|---|---|---|
| L0 协议层 | JSON-RPC 合法性、`isError`、output schema、类型/必填/枚举 | Pydantic / json-schema |
| L1 确定性领域层 | 数值域（0≤比例≤1、cited_by≥0、year≤今年）、跨字段一致、引用完整性、单位、白名单、时效、去重 | 代码规则 + 库比对 |
| L2 交叉验证层 | 关键数值用**独立第二源重算**（OpenAlex ↔ Crossref ↔ 本地图库） | 代码 |
| L3 统计异常层 | 与历史分布比较（z-score/IQR）、计数突变 | 统计代码 |
| L4 语义判读层 | 摘要是否真的支持该断言、相关性 | LLM-judge（rubric + 异源 + 抽样） |
| L5 人工层 | 校准 judge、疑难样本 | 人工抽查 |

**结论口径**：**数值合理性 90%+ 用静态/确定性判定即可，LLM 只处理开放语义问题**；关键动作 **fail-closed**（校验不过 → 不写图库、不进证据池、不写报告）。

# 模块三：初步可行性验证

> 对应文档：`docs/implementation/phase0-implementation-steps.md`（Step 0–8）、`prototype/RESULTS.md`（v1.0 定稿）。
> **讲法**：每个模块都按同一四段式讲——**为什么必须验证 → 验了什么 → 数字 → 结论与对设计的影响**。

## 3.0 先说方法论：为什么"跑通"不算验证（5 条原则，这一段最加分）

1. **先问"什么问题会让结论失效"**，再设计验证（不是"跑一遍看看"）；
2. **计数对账 / 断言**：写入后必须 `expected vs actual` 对账——因为很多错误**不报错**；
3. **确定性注入**：故障用"臂文件 + `os._exit`"而不是掐时间 Ctrl+C，保证可复现；
4. **手工抽查**：指标必须能被独立复算一次（我们抽查了一个 run，事件侧与产物文件完全一致）；
5. **可复现**：LLM 响应内容寻址缓存 → 重跑不花钱且逐字节一致（**确定性来自缓存，不是来自模型**）。

> **PPT 映射**：本模块在 deck 中出 **8 页，一页一个验证**，每页统一三段式：**Why（为什么要这个验证）/ What we did（做了什么）/ Results（结果如何）**，页脚一行 **Impact**；
> 每页 hero（v2）取其**结论式 claim**（如第 16 页「三库撑住 5k 篇且无需换库」、第 17 页「向量延迟是部署选择而非设计缺陷」、第 20 页「每一次注入都被检出且无假警报」），**逐页原文见 §6.1**。

## 3.1 数据源（S1 + S1b）：为什么必须验证

**风险**：如果 OpenAlex 覆盖不到目标会议，整个"周更发现新论文"的前提就不成立；如果引用元数据稀疏，作者的"论文关联图"就是空的。
**验了什么**：白名单 3 年召回量、arXiv 与 OpenAlex 的收录关系、宽召回 vs 白名单的重叠、去重必要性、引用完整率、增量游标语义、限速。

| 结果 | 数字 | 对设计的影响 |
|---|---|---|
| 白名单是**主通道** | 3 年 **386 篇**（≈129/年，下限）；白名单↔宽召回 Jaccard **0.004–0.014** | 检索必须显式白名单过滤 + 多查询扩展（否则系统性漏目标会议） |
| arXiv 价值在时效 | 预印本 OpenAlex 收录率 **91.7%** | arXiv 作辅源补新鲜度，不做主通道 |
| 去重必须做 | 同标题多记录 **19.3–19.8%** | D6 三段式去重 + `merged_ids`（已立 ADR-0001） |
| 引用元数据稀疏 | 白名单引用完整率 **1.5%/14.3%**（宽召回 25–27%；DOI 交叉核对确认**非版本问题**） | 引用图必须 `cited_by` **反向构边**（F6） |
| 增量不能用 `updated` | `from_updated_date` → **429 付费专属**；`from_publication_date`+cursor 稳定（page2 overlap 0） | 增量改用**发表日水位线** + 日期合理性过滤（实测到 2050 年未来日期） |
| 细节 | 白名单 OA **100%**、宽召回 90–93%；礼貌池 20/20 无 429（p50 1.09 s） | 全文可得性好 → grounding 可行；礼貌池策略有效 |

## 3.2 存储栈（S3 + S3b）：为什么必须验证

**风险**：三库方案是架构基石（真相源/图/向量分工）；若图库或向量库在万级规模下不可用，"三存储"要整体返工。
**验了什么**：5k 规模导入、四类查询延迟、幂等重导、删库重建、磁盘、单写者语义、边界数据；向量延迟归因。

| 结果 | 数字 | 结论 |
|---|---|---|
| 图库成立 | 图 2-hop p95 **4.42 ms**、作者聚合 p95 5.06 ms | **不需要换 Neo4j/Milvus** |
| 幂等与可重建 | 重导 233 s 计数零增长；删库重建 376.53 s 计数一致 | 真相源可重建派生索引 |
| 磁盘可控 | kuzu 12.89 + qdrant 49.06 + sqlite 2.95 = **64.9 MB/5k** | 容量无忧 |
| ⚠️ 向量未达标 | top-10 p95 **155 ms**（目标 100 ms） | **已归因**：Qdrant **local 无 ANN**（纯算力仅占 0.3%，74% 是 payload 过滤），线性 0.038 ms/点 → 2 万篇 ≈0.76 s/查询；local = **精确 kNN，召回反而更高** |
| 三条存储约束 | Kuzu 是单文件；仅 `Database.close()` 落盘；非 ASCII 路径不可用 | 已回写 ADR-0003 |

## 3.3 断点续跑（S4）：为什么必须验证

**风险**：周更无人值守，崩溃不可避免；如果"恢复"其实是从头重跑，会重复抓取、重复调用、重复写索引（**不报错但烧钱且污染状态**）。
**验了什么**：6 场景（对照/单崩/连崩/输入漂移/重复触发/正确续跑），3 次 `os._exit(9)` 硬杀。

| 结果 | 数字/现象 |
|---|---|
| 恢复粒度 | **节点边界**（`next=('transform',)`）；checkpoint 库 28–37 KB |
| **正确姿势** | `invoke(None)` → 最终状态与不中断对照**逐字段一致** |
| **陷阱** | 带完整输入 `invoke` → **从 START 重跑已完成节点**（fetch 2–3 次） |
| 幂等义务 | 崩溃节点**必然重跑** → 节点副作用必须幂等 |
| 框架不拦的两件事 | 输入漂移、重复触发已完成 run → 新增守卫 **G15** |
| 事件连续性 | 6 run / 3 次硬杀 / 68 条事件，seq **1..N 连续无重复** |

## 3.4 闭环（S5）：为什么必须验证

**风险**："设计上能跑通"与"真的能产出可核验报告"是两回事；成本与接口可行性也要数字。
**验了什么**：单 topic 端到端（fetch→normalize→chunk→store→retrieve→LLM 抽卡→LLM 生成报告→claims/citation 校验→事件），**真实云端 LLM**。

| 结果 | 数字 |
|---|---|
| 报告 | **8,941–10,821 字 / 16–23 claims / 100% 带可回查引用**（引用 12 篇） |
| 成本 | 冷启动 **$0.0036–0.0126**（60–91 s，6–7 次网络调用含重试）；**缓存重跑 $0 / 0.08–0.12 s** |
| 幂等 | 重跑论文新增 0；缓存命中时 claims 文件 **sha1 完全一致** |
| 事件 | **33–34 条/run**，seq 连续 |
| 关键工程发现 | `deepseek-flash` 是 **reasoning 模型**：`max_tokens` 偏小 → `content=''` + `finish_reason='length'`（**静默空输出**）→ 网关判失败并放大预算重试 |

## 3.5 守卫（S6）：为什么必须验证

**风险**：自愈是论文卖点，如果"守卫只是写了函数"而没测过检出与误报，就是空谈；而且**阈值不能拍**。
**验了什么**：三守卫 + 预算看门狗 + **确定性故障注入**（6 场景 ×3 次，含真实离题语料作负样本）。

| 结果 | 数字 |
|---|---|
| 阈值标定（本步最大发现） | 关键词 scope 表示下正/负**分布重叠**（0.000–0.165 vs 0.000–0.029）→ **无可用阈值**；改用**种子语料质心**后 min(正)=0.0885 > max(负)=0.0670 → **block 0.0777 / warn 0.0867 → TPR 1.0 / FPR 0.0** |
| 注入矩阵 | 5 类注入各 3 次**检出率 1.00**；正常 run **误报 0/3**；18/18 run 按规则"恢复或终止" |
| 预算阶梯 | 80% warn（不阻断）→ 100% stop（abort）完整可见 |
| 事件链 | `tool_call → guard_trigger → recovery{恢复包} → metric` 可读作"起因→检出→处置→结果" |

## 3.8 讲 5 个"静默错误"（比讲"我做了什么"更有冲击力）

> 定义：**不报错、结果看着正常、但结论是错的**。这类问题只能靠对账/断言/分布检查发现。

1. **Kuzu 库是文件**：`rmtree(ignore_errors=True)` 静默不删 → 旧库跨运行累积（`expected_authors=631 / actual=957`，差集"只多不少"）。
2. **Kuzu 只在 `Database.close()` 落盘**：关闭前统计磁盘读到 **0.0 MB 假值**（0.004 → 2.426 MB）。
3. **`MATCH+MERGE` 边端点缺失时静默不写** → 只能靠写入后计数对账发现。
4. **reasoning 模型截断**：`content=''` 却"调用成功" → 网关判失败并放大预算重试。
5. **带输入 `invoke()` 会从 START 重跑**已完成节点 → 结果对、**副作用重复**（fetch 2–3 次）。
6. （备选）**超时只写日志没写事件** → 指标里该族检出率**恒为 0**；**warn 阈值拍常数** → 正常 run 全误报。

# 6. PPT 分页稿（21 页，与 prompt 逐页对应）

> 本节是 `group-meeting-ppt-prompt.md`（Roster + 附录 C）的**中文对照版**：同页数、同标题、同 Hero。

## 6.0 排版规则（两处共用）

**Hero 写法（v2：hero 必须自解释）** —— 每页最多一个 Hero，它不是裸数字，而是一张 accent 浅底卡片上的两行：

1. **Claim**：一句 ≤18 词、**不含数字**的平实判断（26–30px，ink）——"什么成立、为什么重要"；
2. **Evidence**：支撑该判断的数字 + 每个数字**说清它是什么**（14–16px，muted）——阈值/比率/分位数必须解释成话；
3. 若一个事实说不成话（只剩两个词 + 一个数），**删掉这张卡**，把事实并进 `[2]`/`[3]`；
4. **设计页**的 Hero 讲**机制**，**验证页**的 Hero 讲**结论**；Hero 不带 caveat（caveat 一律下沉到 `[3]`）。
