## 2. 难点 1：长时运行的方向固定与自愈机制（详细预想）

### 2.1 为什么难
- 一次周更是**无人值守的长链**（检索→建图→分析→报告），早期一步出错会被后续步骤放大（幻觉级联、主题漂移、死循环、成本空耗）。
- 模型本身非确定、不可信"自觉"——必须靠**外部可判定的守卫 + 显式恢复路径**。
- 自愈不能只"重试"：要能识别故障类型、回退到正确节点、并把"发生了什么"注入后续上下文。

### 2.2 总体框架：三层防线
```
防线1 运行时守卫（每一节点前后）→ 防"跑偏"
   漂移/循环/停滞/schema/引用 检测 → 触发条件边
防线2 状态机纪律（全局）      → 防"失控"
   结构化产出 · 超时/轮次上限 · checkpoint 恢复 · 升级阶梯
防线3 事后质检与反哺（run 末）  → 防"劣质产出过关"
   quality_guard + LLM-judge + grounding 检查 → 不合格重写 / 标注人工复核
```

### 2.3 方向锚定（anchor）机制——防漂移的第一性设计
- **唯一基准**：每个 topic 的 `scope_statement`（边界 + 目标 + 反例说明）是漂移检测与提示注入的锚点，**任何 agent 的 system 都注入 scope + 本 run 目标 + 已确认事实清单**。
- **检索强约束**：检索 agent 的查询先过"意图分类 + scope 相关性过滤"；只允许白名单源（arXiv/OpenAlex/自定义）；越界结果标记不采用。
- **事实纪律（防幻觉级联）**：所有断言必须来自工具结果/库，携带 citation；无支撑内容强制标注"待核实/推测"，不允许静默编造。
- **反漂移反馈回路**：run 结束后 quality_guard 对报告打"scope 相关度分"，写回 topic 状态，影响下一周 scoping 参数（越漂越收紧）。

### 2.4 检测器设计（触发条件/判定/初始阈值/处置）
| 检测器 | 判定方法 | 初始阈值（待实测调） | 处置 |
|---|---|---|---|
| 主题漂移 scope-drift | 阶段性产出(检索 query/摘要/报告片段) embedding 与 scope_statement 余弦 | < 0.6（按嵌入模型调） | 回 planning/scoping，附 feedback |
| 检索漂移 retrieval-drift | 检索结果 out-of-scope 占比 | > 30% | 收紧查询 → 重检索 |
| 死循环 loop | 最近 k 个工具调用签名成环 / 状态哈希重复 | k=5 或连续 3 次同环 | 强制 replan（清局部子状态） |
| 停滞 no-progress | 新增"事实增量"≈0（结构化状态对比） | 连续 2 步增量 0 | 重试→换 provider→终止留痕 |
| 结构化违规 | 阶段产物 Pydantic 校验失败 | 任何一次 | 重试 1 次 → 换档 → 终止 |
| 引用不可回查 | citation 在库/摘要中无匹配 | 任何一条 | 标记"待核实"，不算致命但进报告瑕疵 |

### 2.5 自愈路径与升级阶梯
```
retry(≤2, 退避) → degrade(换 provider/模型档, 见模块2) → replan(回退到 planning/scoping, 带失败原因)
→ abort + annotate(写事件与报告标记, 不阻塞下周)
```
- **恢复信息注入（自愈的关键细节）**：每次降级/重试/replan 时，把"刚刚发生了什么 + 当前可信状态 + 接下来做什么"结构化注入模型上下文——避免模型在不知道自己刚失败过的情况下继续。
- 每步都写 `guard_trigger` / `error` / `recovery` 事件 → 供 Report 页展示、评测统计自愈成功率。

### 2.6 在 LangGraph 上的实现预想
- 节点 = 阶段/角色 agent；**条件边 = 2.4 的处置路由**；守卫做成"节点前后执行的 Python 函数"（框架无关逻辑，可单测）。
- checkpoint（langgraph-checkpoint-sqlite）语义需明确：恢复点粒度 = 节点边界；"恢复后注入"依赖状态里的结构化上下文而非原始对话。
- **测试钩子（fault-injection hook）必须从 P2 就存在**：允许测试脚本注入"越界检索结果/重复工具序列/模拟超时/错误产出"，守卫代码与生产共用同一路径——这是"自愈功能本身可测"的前提（详见 `evaluation-plan.md` §3.3）。

### 2.7 待细化/工程化
- 阈值标定方法（用录制回放跑阈值扫描）；检测器误报/漏报代价定义；
- checkpoint 与事件表的一致性（恢复后事件不重不漏）；
- 重跑策略：失败 run 的下一周是"补跑"还是"顺延"。

## 3. 难点 2：论文关联与作者动向分析

- 为什么难：关系"口径"与"度量"没有标准答案；同名消歧是公认难题；跨 topic 作者一致性要维护。
- 方案预想：
  - **元数据级起步**（引用/共著/主题相近，来自 API 元数据），稳定键（paper_id/author_id）全局统一，schema 预留合并机制（消歧二期）；
  - **时间显式建模**：每条边带年份/发现时间 → 作者动向 = 窗口聚合：近 N 年发文量、合作者集合逐年差异、论文主题质心（embedding）逐年位移；
  - **novelty 判定**：检索命中但图中无 BELONGS_TO 的新 paper_id → 候选"新出现论文"（结合 Qdrant payload）；
  - 图谱查询全部收敛在图服务（Kuzu），前端只调接口，不裸查。
- 待细化：作者动向的具体度量公式（活跃度/方向演变指数）与可视化口径。

## 4. 难点 3：多 agent 长跑中的上下文管理与折叠

- 为什么难：run 跨小时级，状态/工具结果/检索历史会无限膨胀；本地引擎窗口与显存更紧。
- 方案预想：LangGraph 状态只保留**结构化摘要 + 指针**；工具结果用后即折叠（摘要节点）；注入槽固定（scope/当前步/结果卡片）；超预算先折叠再升档（本地→云）。token 计量贯穿（模块2 的 llm_calls）。
- 待细化：折叠粒度与"摘要丢失细节 vs 成本"的平衡实验；对话与周更各自的记忆策略。

## 5. 难点 4：双引擎路由在无人值守下的稳定性与成本

- 为什么难：周更期间无人盯着 provider 故障/限流/质量波动；成本无上限会失控。
- 方案预想：熔断器按 provider 独立（closed/open/half-open）；升级阶梯中 degrade 有明确路由规则（模块2）；**run/topic 级成本预算**：超预算自动降级本地或截断并留痕；敏感度策略为强制拦截（网关层）。
- 待细化：熔断阈值、成本预算默认值；云与本地质量差大时的降级策略取舍。

## 6. 难点 5：增量同步、去重与幂等

- 为什么难：arXiv/OpenAlex 更新语义不同；重复抓取、论文版本更新、失败后重跑都可能污染语料与评测。
- 方案预想：统一 Paper 模型 + canonical paper_id；增量按 updated 时间戳 + sha 指纹去重；**解析/嵌入/图写入全部幂等**（以 paper_id 为键 upsert）；同步游标落 SQLite（sync_state），失败断点续传。
- 待细化：arXiv 版本(v1/v2)与 OpenAlex 记录的合并策略；自定义源（期刊/会议白名单）的增量实现。

## 7. 难点 6+7：可观测回放与无人值守运维

- 方案预想：事件表为唯一真相源（phase/tool/llm/guard/message/error/metric），Report 页回放 = 事件时间线；LLM sampling 参数随事件记录 → 复现实验固定配置；录制-重放测试（用录制 LLM 交互做守卫单测）。
- 运维：job 级看门狗（超时/轮次/存储水位）；同一 topic 串行锁；进程重启后中断 run 标记 interrupted 可手动重跑；DB/图/向量定期快照与清理策略。

## 8. 对未来架构的准备（工程化预留点）

- 抽象接口先行：`guard 接口`、`事件 schema`、`fault-injection hook`、`provider 注册表`、`图/向量/关系存储接口`（换实现不影响上层）。
- 扩展点：更多 provider（含未来可能的 Jetson 本地后端——设备/进度未定）；VLM 图文解析进解析管道；全文级引用图（GROBID）；作者消歧二期；多用户与鉴权。
- 迁移友好：SQLite→PostgreSQL、Kuzu→Neo4j、Qdrant 本地→server 均只需换存储实现层。
